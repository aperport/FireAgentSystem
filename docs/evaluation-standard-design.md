# 消防后勤智能助手 — 精益管控评价标准设计方案

> 文档日期：2026-07-10
> 状态：讨论稿，待明日会议确认

---

## 一、问题背景

当前 `fire-management-analyst` 子智能体通过 Java 后端获取管理数据（巡检、维修、值班等），由 LLM 生成报表和评价建议。

**核心问题：LLM 不知道消防领域的"好"与"坏"标准**

- Java 后端只能做简单阈值判断（完成率 > 95% = 达标）
- LLM 无法理解"为什么"（如"完成率 94% 为什么算需关注"）
- 建议空洞（"建议加强执行力度"等废话）

---

## 二、设计思路：三层评价 + 知识库驱动

### 2.1 三层架构

| 层级 | 来源 | 作用 | 当前状态 |
|------|------|------|----------|
| **原始数据** | Java 后端 | 提供实际值、目标值、环比 | ✅ Mock 已实现 |
| **评价标准** | GraphRAG 知识库 | 提供"什么是好/坏"的法规/行业依据 | ❌ 待实现 |
| **综合解读** | LLM | 结合数据 + 标准 → 生成有依据的评价和建议 | ⚠️ 建议空洞 |

### 2.2 核心改进

**1. 不要只给 LLM 数据，要给标准**

- ❌ "完成率 94.5%，评价一下"
- ✅ "完成率 94.5%，法规要求 ≥ 95%，行业标准 90-95% 为需关注，评价一下"

**2. 建议要具体，不要空话**

- ❌ "建议加强执行力度"
- ✅ "建议：① 在 ICU 病房等高风险区域增加每日巡检频次至 2 次；② 设置逾期预警，超过 24 小时未完成的巡检自动提醒负责人"

**3. 追溯来源**

- "根据 GB 50974-2014 第 3.0.2 条，消防设施应定期检查..."
- "参考《医疗机构消防安全管理规范》第 12 条..."

## 三、实现方案

### 方案 A：评价标准文档入库（推荐）

**新增文档类型：评价标准 Markdown**

```markdown
# 巡检管理评价标准

## 法规依据
- GB 50974-2014 第 3.0.2 条：消防设施应定期检查
- 《医疗机构消防安全管理规范》第 12 条：每日巡查不少于一次

## 评价指标
| 指标 | 达标线 | 警戒线 | 评价 |
|------|--------|--------|------|
| 巡检完成率 | ≥ 95% | 90-95% | 低于 90% 严重不达标 |
| 逾期率 | ≤ 5% | 5-10% | 高于 10% 严重不达标 |
| 异常发现率 | — | — | 无固定标准，需结合历史趋势 |

## 常见问题及改进建议
- 完成率低 → 检查人员配置、巡检路线优化、移动端提醒
- 逾期率高 → 设置预警机制、自动派单、绩效考核
```

**入库流程：**
```
评价标准 Markdown → md_parser → splitter → embedding → PG 向量表
```

**查询方式：**
```python
# 查询时先检索评价标准
standard_docs = knowledge_search("巡检完成率评价标准")
# 再结合原始数据生成评价
prompt = f"""
## 评价标准
{standard_docs[0].page_content}

## 原始数据
巡检完成率：94.5%（目标 95%，环比 -0.5%）

## 要求
1. 逐项评价
2. 综合评价
3. 具体改进建议
"""
```

### 方案 B：Neo4j 图结构存储评价标准

```cypher
// 创建评价标准节点
CREATE (s:EvaluationStandard {
    name: "巡检完成率",
    metric: "completion_rate",
    target: 95.0,
    warning: 90.0,
    unit: "%",
    regulation: "GB 50974-2014"
})

// 关联到法规
MATCH (r:Regulation {code: "GB 50974-2014"})
MATCH (s:EvaluationStandard {name: "巡检完成率"})
CREATE (r)-[:定义了]->(s)

// 关联到模块
MATCH (m:Module {name: "巡检管理"})
MATCH (s:EvaluationStandard {name: "巡检完成率"})
CREATE (m)-[:评价指标]->(s)
```

**查询方式：**
```python
# 查询模块的评价指标
graph_query("巡检管理")  # → 返回关联的评价标准 + 法规
```

## 四、待讨论问题

### 4.1 评价标准来源

| 来源 | 优点 | 缺点 |
|------|------|------|
| 法规条文 | 权威、可追溯 | 条文分散、需人工整理 |
| 行业标准 | 实用、可操作 | 权威性不如法规 |
| 医院内部制度 | 贴合实际 | 通用性差 |
| 历史数据趋势 | 动态、个性化 | 需要积累数据 |

**问题：评价标准从哪来？人工整理法规？还是让 LLM 从法规中抽取？**

### 4.2 评价标准更新

- 法规更新后，评价标准如何同步？
- 不同医院/区域的标准可能不同，如何适配？
- 季节性因素（如夏季用电高峰）如何纳入评价？

### 4.3 工具改造

**当前 `fire_quality_evaluate` 返回预评价结果：**
```python
{
    "overall_rating": "良好",  # Java 后端已判断
    "modules": [...]
}
```

**建议改造为返回原始数据：**
```python
{
    "modules": [
        {
            "module": "inspection",
            "metrics": [
                {"name": "完成率", "value": 94.5, "target": 95.0, "change_pct": -0.5}
            ]
        }
    ]
}
```

**问题：是否让 Java 后端只做数据聚合，不做评价判断？**

### 4.4 LLM Prompt 设计

**当前 Prompt 问题：**
- 没有评价标准输入
- 建议生成缺乏约束

**建议 Prompt 结构：**
```markdown
## 角色
你是消防后勤管理分析专家，熟悉消防法规和行业标准。

## 评价标准（从知识库检索）
{retrieved_standards}

## 原始数据（从 Java 后端获取）
{raw_data}

## 要求
1. 逐项评价：每项指标是否达标，依据什么标准
2. 综合评价：整体运行质量，主要问题
3. 改进建议：具体、可执行、有依据
4. 引用来源：标注法规条款或标准编号
```

## 附录：Agent 在 B/S 架构消防系统中的高价值应用场景

> 筛选原则：
> 1. **排除实时性**：火灾发生时不会用 AI 决策，人的反应更快
> 2. **排除 Java 易实现**：系统层已有 Java 后端，Agent 只做 Java 做不了的

### 一、已覆盖场景

| 场景 | 子智能体 | 说明 |
|------|---------|------|
| 消防知识智能问答 | `fire-qa-assistant` | 法规条文理解、跨文档关联、自然语言交互 |
| 管理质量评价与改进建议 | `fire-management-analyst` | 结合法规标准 + 历史数据 + 行业经验做综合判断 |

### 二、高价值待拓展场景

#### P1 — 消防培训内容生成

- **场景**：根据员工岗位、考核薄弱点，自动生成个性化培训材料
- **为什么适合 Agent**：
  - 需要理解岗位差异（巡检员 vs 值班员 vs 管理员）
  - 需要结合法规 + 案例 + 操作规程生成针对性内容
  - Java 只能做固定模板，无法做个性化生成
- **技术**：RAG + 用户画像 + 内容生成

#### P1 — 法规合规性审查

- **场景**：审查管理制度、操作规程是否符合最新法规
- **为什么适合 Agent**：
  - 需要理解法规条文的语义，不只是关键词匹配
  - 需要跨法规对比（新法规 vs 旧制度）
  - 需要指出具体不合规点并给出修改建议
- **技术**：RAG 法规库 + 文档对比 + LLM 推理

#### P2 — 事故案例分析与学习

- **场景**：输入事故描述，检索相似历史案例，生成分析报告
- **为什么适合 Agent**：
  - 需要语义理解事故描述（同一件事不同说法）
  - 需要跨案例归纳共性和差异
  - 需要生成结构化的"经验教训"
- **技术**：案例知识库 + 语义检索 + 归纳生成

#### P2 — 消防演练方案策划

- **场景**：根据建筑特点、历史隐患、季节因素，生成演练脚本
- **为什么适合 Agent**：
  - 需要多维度信息融合（建筑结构 + 设备分布 + 人员密度 + 历史问题）
  - 需要创造性生成场景（模拟不同火灾类型、不同时间段）
  - Java 规则引擎无法生成"有创意的"演练场景
- **技术**：知识图谱 + LLM 生成 + 场景模板

#### P3 — 消防知识库自动维护

- **场景**：自动发现知识库中的过时内容、矛盾内容、缺失内容
- **为什么适合 Agent**：
  - 需要理解知识之间的逻辑关系
  - 需要发现"这个法规更新了，但相关制度没改"
  - Java 只能做版本号对比，无法理解语义变化
- **技术**：知识图谱一致性检查 + LLM 对比分析

### 三、排除的场景（及原因）

| 场景 | 排除原因 |
|------|---------|
| 火灾实时报警处理 | 实时性，人的反应更快 |
| 设备故障预测 | Java 后端已有规则引擎/时序分析 |
| 能耗异常诊断 | Java 后端已有阈值/统计方法 |
| 智能排班 | 约束求解，Java 规则引擎可实现 |
| 维保工单自动派单 | 规则匹配，Java 工作流引擎可实现 |
| 供应商评估 | 指标计算，Java 聚合统计即可 |

### 四、优先级排序

| 优先级 | 场景 | 技术成熟度 | 业务价值 |
|--------|------|-----------|---------|
| **P0** | 消防知识智能问答 | 已实现 | 高 |
| **P0** | 管理质量评价 | 已实现 | 高 |
| **P1** | 消防培训内容生成 | 中 | 高 |
| **P1** | 法规合规性审查 | 中 | 高 |
| **P2** | 事故案例分析与学习 | 中 | 中高 |
| **P2** | 消防演练方案策划 | 中 | 中高 |
| **P3** | 消防知识库自动维护 | 低 | 中 |
